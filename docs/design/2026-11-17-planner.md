# Planner

- Issue: #3
- Status: **approved** (2026-11-17); revised during implementation, see §8
- Date: 2026-11-17

## 1. Purpose

Choose a mode (off, low, high) for every quarter hour of the next 24–36 hours. The plan keeps the pond
within the band around the target temperature and minimises electricity cost. It preheats before
expensive periods, so that heating in expensive quarters is rarely needed, and it keeps runs long. The
plan is rebuilt every quarter hour from the measured pond temperature, so prediction errors are corrected
continuously. Only the first quarter of each plan is executed (#4).

## 2. Findings that shape the design

From the reference installation (20-10 to 16-11-2026, quarter-hour prices, simulation with the model of #2):

| Strategy | Cost / 4 weeks | Starts/day | Energy in most expensive 25 % of quarters |
|---|---|---|---|
| Existing automations (measured) | € 89 | 3.5 | |
| Thermostat, low mode only | € 64 | 0.8 | 24 % |
| Optimised plan, ±0.25 K, start penalty | € 58 | 1.3 | 9 % |
| Same, expensive quarters avoided | € 58 | 1.5–1.9 | 1–2 % |

- **Low mode** is the largest saving: it delivers ~1.6× more heat per kWh than high mode.
- **High mode** pays off only if the quarter it replaces costs about 3× as much, because the extra heat
  of high over low is expensive. Within one day that ratio is rare with all-in prices.
- **Price timing** within the band adds ~10 % in winter and more in spring and summer, when the daily
  price spread is larger.
- **Starts** beyond ~1.5 per day save almost nothing.
- **Simple rules do not reach the optimum.** "Start when the price is in the cheapest 40 %" and "run the
  cheapest contiguous block" both scored like the thermostat. A real optimiser is needed.
- **Band width:** a wider band saves little in winter. From ±0.25 to ±0.5 K saves ~€ 1 per 4 weeks once the
  lower mean temperature is accounted for.

## 3. Optimisation

### 3.1 Formulation

Dynamic programming over quarters `t = 0 … N−1` with state (pond temperature `T`, previous mode `p`):

```
V[N](T, p)   = −(T − target) · heat_value                      # value of heat left in the pond
V[t](T, p)   = min over m of  energy(m, t) + start(p, m) + band(T') + V[t+1](T', m)
               with T' = model.step(T, m, T_out[t], starting = (p = off and m ≠ off), cover)
energy(m, t) = P_m · Δt · price[t]
start(p, m)  = start_penalty   if p = off and m ≠ off, else 0
band(T')     = w1 · d + w2 · d²,  d = distance of T' outside [target − band + margin, target + band − margin]
heat_value   = mean(price) · P_low / rate_low                 # € per K, delivered in low mode
```

- `T` on a grid with 0.01 K step from `target − band − 1.5` to `target + band + 1.5` (~350 points).
  `V[t+1]` is evaluated at `T'` by linear interpolation, so the grid does not bias the result.
- The band is a soft constraint with steep penalties (`w1` = 5 €/K, `w2` = 500 €/K² per quarter). There is
  always a solution, even when the pond starts far outside the band; it then returns as fast as allowed.
- `margin` (default 0.07 K) keeps the plan inside the band, so a prediction error of the size measured in
  #2 does not force heating in an expensive quarter.
- `heat_value` stops the plan from emptying the buffer just before the horizon ends.
- High mode can be disabled (option); then `m ∈ {off, low}`.
- The solution is the policy table `argmin[t][p][T]`. The plan is read out by simulating forward from the
  measured temperature and the actual current mode.

Size: N ≤ 144, 3 × 3 transitions, ~350 grid points: about 450 k vectorised operations, a few milliseconds
with numpy. It runs in the executor.

### 3.2 Avoiding expensive quarters

There is no explicit ban. With the cooling in the model and the value of stored heat, the optimiser
preheats before expensive blocks by itself. In the simulation, a hard ban on the most expensive 10 % or
25 % changed the cost by only € 0.2–0.3 per 4 weeks. A ban would also have to be overridden when the pond
reaches the lower bound, so it adds complexity without benefit. The share of energy in the most expensive
quarters is reported (sensor attribute) so this can be checked.

### 3.3 Short cycles

- `start_penalty` (default € 0.05) limits starts to ~1–1.5 per day on the reference data.
- The start factor in the model (first quarter 75 % heat) charges the real start-up loss.
- No hard minimum run time: replanning every quarter could otherwise lock a bad decision in.

## 4. Inputs

### 4.1 Prices

`prices.py` reads the attributes of the configured price sensor. A list entry is accepted when it has a
start time and a value:

| Attribute | Start key | Value key | Example source |
|---|---|---|---|
| `raw_today`, `raw_tomorrow` | `start` (`end` optional) | `value` | EPEX Spot, Nord Pool |
| `today`, `tomorrow` | `time` / `startsAt` | `total` / `price` / `energy` | Tibber, EnergyZero style |
| `prices`, `data`, `forecast` | `start` / `time` / `startsAt` | `value` / `price` / `total` | other price sensors |

The same parser reads solar forecasts (§4.4), where the value key may also be `w` (W) or `kwh` (kWh per
entry, converted to mean kW over the entry).

- Lists of plain numbers (`today: [0.19, …]`) are accepted when there are 24 or 96 entries, starting at
  local midnight.
- Entries without `end` last until the next start, at most 1 hour.
- The resolution may be hourly or quarter-hourly. Hourly prices are spread over 4 quarters.
- **Price forecast (optional second sensor).** It extends the horizon beyond the last known price, for
  example with the `forecast` attribute of a price-forecast integration. Known prices always win.
- **Price basis.** `effective = price · multiplier + addition` (options, defaults 1 and 0). With a bare
  exchange price, the user sets VAT and taxes (in NL: 1.21 and ~0.136) so that ratios between quarters are
  realistic. This matters for high mode and the start penalty. The same transformation applies to the
  forecast sensor, so both must be on the same basis.

### 4.2 Horizon

- From the current quarter to the last quarter with a price, capped at `horizon_hours` (default 36).
- Fewer than 4 hours of prices: the plan uses the mean of the known prices for the rest, up to 24 hours,
  and the mode sensor reports `limited_prices`.
- No prices at all: price 1.0 everywhere, so the plan minimises energy.

### 4.3 Outdoor temperature

- Hourly forecast from the configured weather entity (`weather.get_forecasts`, type hourly), cached for
  1 hour, interpolated to quarters.
- **Bias correction.** The outdoor sensor and the forecast differ (location, sensor in the sun). The
  current difference `sensor − forecast` is added and decays linearly to 0 over 6 hours.
- Without a weather entity or forecast: the current outdoor sensor value for the whole horizon.

### 4.4 Solar surplus (optional)

Own solar power can make some quarters cheaper than the grid price. This is optional; without solar
configuration every quarter uses the purchase price.

**Inputs**

| Option | Meaning |
|---|---|
| Surplus sensor | Either a PV power sensor, or the grid export sensor of the smart meter. A net grid power sensor is also accepted, with export as negative. |
| Sensor type | `pv_power`: surplus = PV − base load. `grid_export`: surplus = export + heat pump power now (the running heat pump already reduces the export). `grid_net`: surplus = −net + heat pump power now, at least 0. |
| Base load (W) | Household consumption subtracted from PV power; only for `pv_power` and for the forecast. Default 300 W. |
| Solar forecast sensor | Optional. Hourly PV forecast with `raw_today`/`raw_tomorrow` or `forecast` lists (e.g. Forecast.Solar, Solcast or a custom forecast). Forecast surplus = max(0, forecast − base load). |
| Feed-in price | `feed_in = price · feed_multiplier + feed_addition` (options), or a feed-in price sensor. Defaults equal the purchase price (net metering): then solar has no effect on the plan. |

**Surplus per quarter**

- The current quarter uses the measured surplus.
- Further ahead the forecast is used, scaled by the ratio between measured and forecast PV now. This
  correction decays to 1 over 2 hours.
- Without a forecast, the measured surplus is held for the current quarter only.

**Cost per mode.** In a quarter with surplus `S` (kW), mode `m` costs

```
covered = min(P_m, S)
cost    = Δt · (covered · feed_in[t] + (P_m − covered) · price[t])
```

So low mode (~0.4 kW) is covered more often than high mode. The optimiser weighs this per quarter like
any other price difference: it preheats in sunny quarters when feed-in is worth less than purchase.

**Notes**

- In the Netherlands net metering ends on 1-1-2027. From then on, feed-in is worth roughly the bare
  exchange price minus a feed-in fee, which is well below the all-in purchase price. Before that date the
  defaults (feed-in = purchase) are correct and solar changes nothing.
- A home battery absorbs surplus that would otherwise be exported. Then the surplus is not free: set the
  feed-in value to what stored battery energy is worth, or leave solar unconfigured. Coordinating with a
  battery is out of scope.
- The P50 forecast is used. A forecast that is too high only costs a little: the plan is rebuilt every
  quarter with the measured surplus.

## 5. Interface (`core/planner.py`)

```python
@dataclass
class PlanRequest:
    start: float                 # epoch of the current quarter start
    pond: float                  # measured pond temperature
    mode_now: str                # current mode (from power or the last command)
    target: float
    band: float
    margin: float
    outdoor: list[float]         # per quarter
    price: list[float]           # effective €/kWh per quarter
    surplus_kw: list[float] | None   # solar surplus per quarter (kW), optional
    feed_in: list[float] | None      # effective feed-in €/kWh per quarter, optional
    params: ModelParams
    cover: bool
    start_penalty: float
    allow_high: bool

@dataclass
class Plan:
    start: float
    modes: list[str]             # per quarter
    temps: list[float]           # predicted pond temperature at the end of each quarter
    prices: list[float]
    energy_kwh: float            # next 24 h
    cost: float                  # next 24 h, €
    starts: int                  # next 24 h
    expensive_share: float       # energy share in the most expensive 25 % of quarters, next 24 h
    next_start: float | None
    next_stop: float | None

def make_plan(req: PlanRequest) -> Plan

# prices.py
def parse_prices(attributes: dict, tz: str) -> list[tuple[float, float, float]]   # (start, end, value)
def to_quarters(entries, start: float, n: int, multiplier: float, addition: float) -> list[float | None]
```

## 6. Tests

- **Prices:** parsing of each supported attribute format (fixtures copied from real sensors), hourly to
  quarter expansion, DST days (92 and 100 quarters), missing tomorrow.
- **Preheating:** with a flat price except a 3-hour expensive block, the plan heats before the block and
  not in it, staying within the band.
- **High mode:** high is not chosen with a daily price ratio of 1.5; it is chosen when one quarter costs
  more than 3× another and the buffer allows it.
- **Starts:** a start penalty of 0 gives more starts than € 0.05; the cost difference is small.
- **Solar:** with a midday surplus and feed-in below purchase, low mode moves into the surplus quarters;
  with feed-in equal to purchase, the plan is unchanged.
- **Soft band:** starting 1 K below the band, the plan heats immediately and continuously.
- **Replay** on the reference dataset (20-10 to 16-11-2026, quarter-hour prices, closed loop: plan every
  quarter, execute the first quarter in the model):
  - within ±0.25 K;
  - ≤ 1.5 starts/day;
  - ≤ 2 % of energy in the most expensive 25 % of quarters;
  - cost within 5 % of the offline optimum;
  - runtime per plan < 50 ms.

## 7. Out of scope

Executing the plan and safety overrides (#4); entities and options (#5); solar gain and wind; several heat
pumps or other loads; coordination with a home battery (the effective prices are taken as given).

## 8. Revisions during implementation (2026-11-17)

**Model values.** The thermal model of #2 was revised: low mode is ~1.45× as efficient as high mode, not 1.6×.
With low mode barely covering the November heat loss (0.117 K/h against 0.07 K/h on average, and more on cold
nights), there is less room to preheat than §2 assumed.

Replay of 20-10 to 16-11-2026, band ±0.25 K, revised model:

| Strategy | Cost / 4 weeks | Starts/day | Energy in most expensive 25 % |
|---|---|---|---|
| Thermostat, low only | € 64.2 | 0.9 | 22 % |
| Planner, closed loop (start penalty € 0.10) | € 61.7 | 1.6 | 11 % |
| Offline optimum (perfect knowledge) | € 61.8 | 1.5 | 11 % |

- **The closed loop matches the offline optimum** within 0.4 %: replanning every quarter with only the prices
  known at the time loses almost nothing.
- **The criterion "≤ 2 % in the most expensive quarters" is dropped.** Heating in an expensive quarter is
  sometimes simply the cheapest option, for example when the alternative is preheating in high mode, which is
  less efficient. The user chose to **optimise on cost**.

**Expensive-quarter surcharge.**
- `EnergyCosts.expensive_surcharge` adds a planning-only surcharge (€/kWh) to the most expensive 25 % of the
  quarters of each 24 h block. Reported costs always use the real prices.
- By default the surcharge is **tuned automatically** (`core/tuning.py`). Every night the last 14 days are
  replayed for the candidates 0, 0.15, 0.30, 0.50 and 1.00 €/kWh: replanning hourly, with only the prices known
  at the time.
- The candidate with the lowest real cost wins; at (near) equal cost (0.5 %) the smallest one wins.
  Candidates that leave the band are rejected.
- On the reference data it picks **0** each time: the candidates differ by less than 0.5 %. The option keeps a
  manual value possible.
- Runtime ~45 s at night, in the executor.
- Samples now also store the effective price per quarter, which the tuning needs.

**Implementation details.**
- **Grid:** 0.02 K, with linear interpolation of the value function on the uniform grid. ~25–45 ms per 36 h
  plan.
- **Modules, one responsibility each:**
  - `timeseries.py`: intervals, values per quarter;
  - `prices.py`: attribute parsers (strategy / chain of responsibility) and `PriceTransform`;
  - `forecasts.py`: outdoor forecast with bias correction, solar surplus;
  - `costs.py`: cost per quarter and mode;
  - `planner.py`: `Planner` protocol, `DynamicProgrammingPlanner`;
  - `tuning.py`: surcharge.
- **Replay test:** runs on one week (`tests/test_replay.py`); the full period runs with `scripts/replay.py`.

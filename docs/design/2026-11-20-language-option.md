# Language option for the integration and the card

- Issue: #28
- Status: **approved** (2026-11-20)
- Date: 2026-11-20

## 1. Purpose

Choose the language of the planner independently of Home Assistant, e.g. an English Home Assistant with a Dutch
pond planner: entity names, explanatory attributes and the card.

Home Assistant itself has two languages:
- the **profile language** of each user: the frontend, config and options flows, repair issues, and translated
  states and attributes in the more-info dialog;
- the **system language**: entity names generated by integrations.

The integration can only change what it produces itself. Screens drawn by the Home Assistant frontend stay in the
profile language (out of scope, see the issue).

## 2. Option

New option `language` in the options flow, last field, as a select with translated labels:

| Value | Meaning |
|---|---|
| `auto` (default) | as now: entity names in the system language, the card in the profile language |
| `en` | English |
| `nl` | Dutch |

Saving the options reloads the entry (existing update listener), so the new names show at once.
`DEFAULT_OPTIONS` gets `language: "auto"`; existing entries without the key read it as `auto`.

## 3. Texts in the integration

New module `language.py` (Home Assistant side; `core/` is not involved):

```python
LANGUAGES = ("en", "nl")

class PlannerTexts:
    """Names and attribute texts of the planner in one language, from the integration's own translations."""

    language: str | None  # None = auto

    @classmethod
    async def async_load(cls, hass: HomeAssistant, option: str) -> PlannerTexts: ...
    def entity_name(self, platform: str, key: str) -> str | None: ...
    def attribute_text(self, platform: str, key: str, attribute: str, code: str | None) -> str | None: ...
```

- `async_load` resolves the option: `auto` → the system language when it is `en` or `nl`, else `en`
  (for the attribute texts only; names stay with Home Assistant). It reads the strings with
  `homeassistant.helpers.translation.async_get_translations(hass, language, "entity", [DOMAIN])`, so the
  existing `translations/en.json` and `nl.json` remain the only source of texts.
- `entity_name` returns `None` for `auto`, so Home Assistant translates the name as now.
- `async_setup_entry` loads the texts once and keeps them in the runtime data next to the coordinator.

### Entity names

`PlannerEntity.__init__` sets `_attr_name = texts.entity_name(platform, key)` when it is not `None`.
`_attr_translation_key` stays, so the card keeps finding the entities by translation key, and entity ids do not
change (they are fixed in the entity registry).

### Explanatory attributes

The codes stay as they are; a readable text is added next to them:

| Entity | Code attribute | New text attribute | Codes |
|---|---|---|---|
| mode sensor | `reason` | `reason_text` | `plan`, `no_plan`, `below_band`, `far_below_band`, `above_band`, `no_pond_temperature` |
| mode sensor | `apply_result` | `apply_result_text` | `sent`, `unchanged`, `dry_run`, `heat_pump_off`, `unavailable`, `error` |
| mode sensor | `price_status` | `price_status_text` | `ok`, `limited_prices`, `forecast_only`, `no_prices` |
| thermostat | `reason` | `reason_text` | as the mode sensor |

The texts live in the standard place, `entity.<platform>.<key>.state_attributes.<attribute>.state.<code>`
(accepted by hassfest), so the more-info dialog also shows translated codes in the profile language.
The new `*_text` attributes are added to `_unrecorded_attributes`.

The mode sensor also gets the attribute `language` with the option value (`auto`, `en`, `nl`) for the card.

## 4. Card

Language resolution (new pure function in `localize.ts`):

```ts
export function cardLanguage(config: CardConfig, plannerLanguage: string | undefined, hass: HomeAssistant): string;
```

1. card option `language` when it is `en` or `nl`;
2. else the integration's `language` attribute when it is `en` or `nl`;
3. else the profile language (`hass.locale.language`), as now.

The result drives everything that is language-dependent: `localizer`, dates (`vr 21 nov`) and numbers.

- **Numbers**: new `numberText(value, digits, language)` in `format.ts` with `Intl.NumberFormat`
  (`0,33` in Dutch). It replaces `toFixed` wherever a number is shown (figures, axes, tooltip, gauge).
  `toFixed` stays for SVG coordinates.
- **Times** stay 24-hour (`clockText`, #26).
- **Editor**: new field `language` (`auto` / `en` / `nl`, default `auto` = follow the integration); the labels
  of the editor follow the resolved language too.

## 5. Tests

- Core: unchanged (no core code).
- Home Assistant (`tests_ha`): option default and migration (missing key → `auto`); with `nl` the entity names
  are Dutch while the system language is English, entity ids unchanged; with `auto` the names follow Home
  Assistant; `reason_text` and friends in the chosen language; `language` attribute; reload on change.
- hassfest: the new `state_attributes` and the option selector translations.
- Card: `cardLanguage` resolution order; `numberText` for `en` and `nl`; dates in Dutch; the editor schema has
  `language`.

## 7. Risk

Home Assistant's frontend can also compute entity names from the translation key in the profile language. If it
does that in some view, the fixed `_attr_name` may not win there. This is checked in the dry-run on Arno's
Home Assistant; if needed the fallback is to drop `_attr_translation_key` when a fixed language is chosen and let
the card find entities by unique id suffix instead.
